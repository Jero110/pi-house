## Executor design decision (binding for this attempt; record it in your commit message)

1. Explicit entry point `migrateLegacyStore(dir, opts)` in new `packages/pihouse/src/workflow/migration.ts`. Nothing
   calls it automatically in this task; activation from real user stores is out of scope (later command cutover).
2. Backup first: copy every legacy file (index.json, flags.json, runs/, digests/, batches/, consulted/, ideas/,
   proposals/, archive/, workflow-memory.md) into `<dir>/migration-backup.incomplete/`, write a manifest of relative
   path -> sha256 -> bytes, fsync-equivalent (write then rename), then rename to `<dir>/migration-backup/`.
   An existing `.incomplete` directory is pihouse-owned partial output: verify it against a fresh manifest of the
   live files; if it matches, finish; otherwise remove ONLY that owned incomplete directory and restart the copy.
   Never touch an existing completed backup; if live legacy bytes no longer match the completed backup manifest,
   stop with a diagnosed error (no silent re-backup, no import from drifted bytes).
3. Import in ONE `BEGIN IMMEDIATE` transaction from the backup bytes, not the live files: every index entry with its
   original id, kind, status, path, title/summary, fingerprint and batch fields; flags; proposals with rejected
   fingerprints; consulted/idea summaries with their body sha256. Add an additive schema version through the existing
   migration mechanism in `storage.ts` if needed (narrow owned edit). Mark every imported run `legacy: true`,
   `coverage: "legacy-unknown"`; a processed legacy run gets `deletionAuthority: "none"`. Legacy "applied" proposals
   import as `legacy-applied-unverified`, never as a verified receipt. Record a migration row
   (`state: imported`, source manifest hash) in the same transaction, then a separate `state: active` marker.
4. Resume: re-running after a crash at any boundary (mid-backup, after backup, mid-import rollback, after import
   before activation) converges to the same rows with no duplicates (use primary keys / INSERT that is idempotent by
   original id and manifest hash).
5. After activation, `openMemory` index reads and writes go through SQLite inside a single transaction per mutation
   (read-modify-write within `BEGIN IMMEDIATE`), so two writers cannot lose updates; prove with two store handles
   (or a child process) mutating concurrently. Before activation, legacy JSON behavior is unchanged, so all existing
   memory/keeper tests keep passing. A corrupt or missing SQLite file after activation is a diagnosed error, never an
   empty memory, and never a silent fallback to JSON.
6. Keep the JSON index only as a backup/export; do not run two independent authorities.
